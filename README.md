# SPW Media Runtime

面向 [Salt Player for Windows（SPW）](https://github.com/Moriafly/SPW) 创意工坊的通用多媒体运行时。

为 SPW 插件提供可复用的音视频处理、视频播放、网页嵌入、媒体分析等能力，统一管理第三方依赖与原生资源，避免不同插件重复集成相同的多媒体组件。

**项目状态：规划阶段，尚未发布可用版本。**

## 项目定位

SPW 已具备音乐播放、歌词显示、曲库管理等功能，并通过 [SPW Workshop API](https://github.com/Moriafly/spw-workshop-api) 向插件开放相应接口。

但当插件需要视频解码、媒体转码、网页嵌入、音频分析等额外能力时，开发者仍需要自行集成第三方库，处理原生依赖、跨平台兼容及资源管理。

SPW Media Runtime 希望为这些需求提供统一的基础设施，使开发者能够专注于插件自身的功能，而不必重复构建底层多媒体环境。

### 设计原则

- **补充而非替代**：优先使用 SPW 已有的公开接口，不重复实现宿主已经提供的能力。
- **按需加载**：仅在插件实际请求时初始化对应模块，避免未使用的组件占用运行资源。
- **共享与隔离并重**：多个插件可以同时使用公共能力，但各自的任务、会话与状态相互独立。
- **跨平台兼容**：提供统一的公共接口，明确标识各平台的可用能力。
- **通用接口**：不绑定特定网站、插件或业务场景，兼顾高级封装和底层能力。
- **状态可观察**：所有模块提供明确的状态、结果和错误反馈，避免内部故障无法被调用方感知。
- **模块化扩展**：不同能力独立演进，新增功能不应要求重构整个运行时。

## 规划模块

| 模块 | 主要技术 | 提供的能力 |
|---|---|---|
| Media Processing | FFmpeg / FFprobe | 音视频转码、解码、格式分析、滤镜及流处理 |
| Media Playback | libmpv | 视频播放、进度控制、硬件解码、同步及播放器管理 |
| Web Engine | WebView2 | 网页嵌入、交互、登录及持久化会话 |
| Media Metadata | jaudiotagger 等 | 媒体标签、元数据、嵌入封面的读取与修改 |
| Audio Analysis | 原生音频采集及分析组件 | 实时频谱、波形、响度及其他音频分析 |
| Media Rendering | Compose / Skia 桥接 | 视频帧交付、图像处理及宿主界面集成 |

以上模块均处于规划阶段。具体底层组件、实现范围及接口可能随开发调整。

### Media Processing

以 FFmpeg 为主要媒体处理后端，提供：

- 音视频解码、编码、转码与重新封装。
- 视频帧、音频流及媒体资源提取。
- 格式、编码、时长及媒体流信息分析。
- 视频缩放、裁切、滤镜与其他处理操作。
- 通用 FFmpeg 参数调用及异步任务执行。

除常用功能封装外，保留通用命令执行能力，避免公共 API 限制 FFmpeg 本身的功能范围。

### Media Playback

以 libmpv 为主要播放引擎，提供：

- 媒体加载、播放、暂停、停止与跳转。
- 播放进度、缓冲、速度和音量控制。
- 视频解码、硬件加速及播放状态事件。
- 独立播放器实例及生命周期管理。
- 视频输出与外部渲染接口。

FFmpeg 和 libmpv 的功能相互补充。Runtime 将研究兼容构建下的底层依赖复用，但允许两个模块独立调用和初始化。

### Web Engine

提供网页嵌入与浏览器会话管理。

计划支持：

- 页面导航、加载状态及错误事件。
- JavaScript 与插件之间的受控通信。
- 独立浏览器实例和持久化 Profile。
- Cookie、LocalStorage 等网站数据管理。
- 登录会话保持、清除及生命周期管理。
- 浏览器进程异常监测与资源回收。

每个插件默认拥有独立的持久化 Profile。同一插件的多个浏览器实例可以复用其会话，不同插件之间的账户数据默认隔离。

当前规划使用 Microsoft WebView2，支持 Windows 平台。

Runtime 仅提供通用浏览器能力，不实现特定网站的业务逻辑。

### Media Metadata

统一提供媒体元数据操作能力，包括：

- 音频标签和基本媒体信息读取。
- 标签字段修改与文件写入。
- 嵌入封面读取、提取和修改。
- 常见音频格式的元数据兼容处理。

优先复用 SPW 已公开的能力，对于未覆盖的操作再通过第三方库补充。

### Audio Analysis

提供可复用的音频采集与分析接口，包括：

- 音频数据采集与订阅。
- 实时频谱和波形分析。
- 响度、峰值及其他音频特征计算。
- 音频指纹等可选扩展能力。

对于多个插件订阅同一音频源的情况，尽可能共享底层采集服务，避免重复采集与计算。

### Media Rendering

提供通用视频帧和图像渲染接入能力。

计划支持视频帧交付、像素格式转换、渲染目标管理及 Compose / Skia 界面集成。

高频视频数据应使用适合的内存或原生渲染通道，不通过普通控制消息逐帧传输。

## Runtime Core

Runtime Core 负责各模块的公共管理机制，保持轻量运行。

### 按需加载

各模块独立管理初始化和运行状态。

1. 插件请求某项能力。
2. Runtime 检查模块、依赖与平台兼容性。
3. 首次使用时加载所需组件。
4. 根据请求创建任务、会话或共享服务。
5. 不再使用时释放相应资源。

未被请求的模块不应初始化，也不应产生持续运行的后台任务。

对于原生动态库，考虑到 JVM 和操作系统的加载限制，不强制在每次使用结束后卸载。应优先释放实际占用 CPU、GPU、内存和系统句柄的运行实例。

如完整依赖包体积过大，后续可以采用独立资源包或按需下载安装机制。

### 多插件并发

Runtime 应允许不同插件同时调用同一项能力。

根据操作类型采用不同的管理方式：

- **独立任务**：转码、文件处理等操作分别执行，通过队列和并发限制协调。
- **独立实例**：多个播放器维护独立的播放状态和资源。
- **共享服务**：对于兼容的音频采集、分析及缓存请求，允许多个订阅者复用结果。
- **受控访问**：对于同一文件的并发写入等操作，提供必要的互斥和一致性保护。

不同插件的任务必须能够独立取消和清理。

一个插件停止使用服务时，不得错误地释放仍被其他插件使用的公共资源。

### 状态与错误反馈

所有模块应提供统一的状态与错误反馈机制。

包括：

- 请求是否被接受。
- 模块是否可用及初始化状态。
- 异步任务的进度和最终结果。
- 长期会话的运行状态与变化事件。
- 结构化错误码、错误详情及重试建议。
- 会话和任务的主动状态查询。

错误信息应能够区分依赖缺失、初始化失败、网络异常、媒体处理失败、渲染故障、资源不足及内部异常等情况。

每次调用关联插件标识、会话标识与操作标识，以支持故障定位。

Runtime 保留必要的诊断日志，但不得将 Cookie、访问令牌等敏感信息写入普通日志。

### 资源与生命周期管理

Runtime 统一管理各模块的任务、会话和原生资源。

- 避免重复初始化相同的公共组件。
- 跟踪资源归属及使用者。
- 支持取消任务、关闭会话和释放资源。
- 对并发任务设置必要的资源限制。
- 对异常退出的子进程进行回收。
- 隔离不同插件之间的可恢复故障。

对于可能导致宿主进程崩溃的高风险原生操作，可根据需要采用独立进程隔离。

## 公共 API 与插件通信

Runtime 通过版本化公共 API 向其他 SPW 插件开放能力。

设计目标：

- 支持插件动态发现 Runtime 和可用模块。
- 支持接口版本与能力协商。
- 不要求调用插件依赖 Runtime 内部实现。
- 兼容 PF4J 插件类加载器隔离机制。
- 支持同步请求、异步任务、事件订阅及状态查询。
- 对原生资源和媒体会话提供明确的所有权与释放机制。

控制命令与高频媒体数据采用适合各自特点的通信方式。

公共接口应尽可能稳定，内部模块可以独立升级，但不得无提示地破坏已有调用方。

## 平台兼容性

各模块的平台支持情况如下。

| 模块 | Windows | Linux |
|---|---|---|
| Runtime Core | 计划支持 | 计划支持 |
| FFmpeg / FFprobe | 计划支持 | 计划支持 |
| libmpv | 计划支持 | 计划支持 |
| Media Metadata | 计划支持 | 计划支持 |
| Web Engine | WebView2（计划支持） | 暂不支持 |
| Audio Analysis | 计划支持 | 待确定 |
| Media Rendering | 计划支持 | 待确定 |

实际支持范围以正式发布版本及对应模块文档为准。

插件可通过公共 API 查询模块的可用性和支持能力，并获得明确的不可用状态或错误信息。

## 第三方依赖与许可证

Runtime 将集成来自不同开源项目的第三方组件。

各组件的许可证、构建选项及再分发条件可能不同，需要分别核查。

项目将维护独立的第三方组件清单、许可证声明及必要的源码或构建信息。

对于存在许可证限制的依赖，应根据实际使用和分发方式选择合适的构建版本，不假定不同许可证的组件可以直接合并分发。

项目自身的许可证将在确认整体依赖关系后确定。

## 开发路线

- **Runtime Core**：公共协议、模块管理、按需加载、并发调度与状态反馈。
- **基础媒体能力**：FFmpeg / FFprobe 和媒体元数据接口。
- **视频播放与渲染**：libmpv、播放器实例管理及渲染桥接。
- **网页运行环境**：WebView2 与持久化会话管理。
- **音频分析**：统一音频采集、分析及共享订阅。
- **开发者生态**：完善 SDK、接口文档、示例与第三方插件接入支持。

模块可独立开发和逐步发布，不要求所有规划功能同时完成。
