# 架构贡献规范

本文适用于修改 SPW Media Runtime 公共接口、运行时核心、能力模块、原生依赖及平台适配的 Pull Request。

SPW Media Runtime 是供多个创意工坊插件共同使用的上游基础设施。架构变更应以**下游兼容性、模块可扩展性、依赖复用和运行可靠性**为审查基准。本文描述贡献需要维持的技术契约；具体模块是否已经实现，以代码与发布记录为准。

提交变更前请先阅读 [贡献指南](../CONTRIBUTING.md)。

## 1. 分层与职责

```text
Consumer Plugins
       │
Public SDK / Versioned Contracts
       │
Runtime Core
  ├─ Capability Registry & Negotiation
  ├─ Invocation & Event Delivery
  ├─ Lifecycle & Resource Ownership
  ├─ Scheduling & Diagnostics
  └─ Platform / Dependency Discovery
       │
Module Provider Contract
  ├─ FFmpeg / FFprobe
  ├─ libmpv
  ├─ WebView2
  └─ Other Media Providers
       │
Managed Native Assets / Platform Backends
```

| 层级 | 职责边界 |
| --- | --- |
| Public SDK | 提供轻量、版本化的公共数据契约与调用入口；不携带媒体库实现或大型原生资源 |
| Runtime Core | 负责通用能力注册、路由、状态、权限边界、并发及资源生命周期 |
| Module Provider | 声明能力、依赖、兼容范围和资源管理方式；实现具体媒体功能 |
| Native Assets / Backend | 维护平台相关可执行文件、动态库及原生交互细节 |
| SPW Adapter | 处理宿主插件生命周期、权限及宿主 API 的对接 |

**扩展能力应优先通过注册新 Provider 实现。** Core 不得包含持续增长的模块专属分支，也不应直接依赖 FFmpeg、libmpv 或 WebView2 的实现类型。确需变更 Core 的 PR，应说明已有扩展契约为何不适用，并评估对既有调用方的影响。

## 2. 公共契约与兼容性

任何跨插件公开的协议或类型，均视为长期维护的接口。相关 PR 需要说明：

- **能力标识与发现**：采用稳定标识和能力查询；允许新版 Runtime 注册旧调用方未知的能力。
- **版本协商**：区分 SDK/API、协议、模块实现及原生依赖的版本。调用方通过所需能力和协议版本判断兼容性，不依赖 Runtime 总版本推断全部功能。
- **消息兼容**：明确字段默认值、可选字段、未知字段、枚举扩展及不支持操作的处理方式。
- **执行语义**：明确定义同步结果、异步完成、取消、超时与重复调用的行为。
- **错误契约**：错误码及其含义稳定，模块内部异常经适当转换后反馈给调用方。
- **弃用流程**：优先提供兼容扩展和迁移期；无法避免的不兼容变更须单独说明影响范围与迁移方式。

不得将私有实现类、可变内部状态、原生指针或不明确所有权的对象直接作为公共契约。变更公开 API 时，须同时更新对应参考文档与示例。

## 3. 跨插件与原生组件边界

SPW 创意工坊使用 PF4J；不同插件可能由独立类加载器加载。贡献不应假定任意 Kotlin/Java 对象都能够跨插件直接传递并保持类型身份。

- 对外通信使用与实现类解耦、可版本化的数据类型和稳定协议。
- SDK 隐藏通信、原生库加载及平台后端选择等内部机制。
- 命令、状态事件与高频媒体数据应采用适合各自负载的通道；不通过普通控制消息逐帧复制视频或大量 PCM 数据。
- 原生调用须明确线程约束、回调归属、对象有效期及故障边界。
- 不假设任意不同 ABI 版本的 FFmpeg/libmpv 可以在同一 JVM 中安全共存；有冲突时应提出版本约束或进程隔离方案。

## 4. 共享依赖与按需运行

共享依赖是项目存在的主要理由。提交模块或更换依赖时，应检查最终分发结构是否仍避免下游插件重复携带同一组件。

必须区分：

1. **统一分发**：共享媒体二进制由 Runtime 维护，调用插件仅依赖轻量 SDK。
2. **按需初始化**：未被使用的重型模块不创建播放器、转码进程或持续采集任务。
3. **运行态隔离**：相同模块可被多个插件使用，但任务、播放器和账户会话拥有明确的调用方归属。
4. **按场景共享**：兼容的采集、缓存和底层服务可复用；不应为了节省资源而强行共享不兼容的播放状态。

模块应显式管理资源的获取、释放、取消及异常清理。公共资源不得因为一个调用方退出而误释放；清理操作应能安全处理重复执行。

动态库被 JVM 加载后不一定能可靠卸载，因此不得把“使用结束后卸载 DLL/SO”作为默认保证。延迟初始化也不等于缩小安装包；二进制分发策略须单独评估。

## 5. 并发、状态与故障处理

跨插件并发是常规场景，不应作为特殊例外处理。

- 独立任务应具有独立的标识、执行状态、取消行为和结果。
- 共享服务须有订阅者管理与资源引用关系，并考虑队列、背压、限额和同一文件的并发写入。
- 一次性任务应提供可观察的终止结果；长期会话应支持状态查询和事件订阅。
- 状态与错误关联调用插件、会话及操作标识，提供稳定错误码与必要的诊断上下文。
- 子进程异常退出、原生库不可用、资源耗尽等情况需要可恢复或可诊断的反馈，不能仅写入 Runtime 日志。
- 单一任务失败不应导致无关任务失效；进程内原生崩溃无法保证隔离时，应审查进程隔离的必要性。

涉及账户的模块应将持久化与隔离同时考虑：同一插件的会话可在重启后保留，不同插件默认不能访问彼此的 Cookie 或认证材料。日志和错误对象不得泄漏凭据。

## 6. 平台与能力声明

模块需声明其实际支持的平台、架构、依赖条件和功能限制。Runtime 存在不等于所有模块可用；不支持的能力应返回明确状态。

平台后端可以不同，但应维持同一公共契约的语义。平台差异应通过能力发现暴露，而不是依赖调用方猜测或解析底层异常。

## 7. 架构类 PR 的审查材料

涉及公共接口、模块注册、原生依赖或运行时生命周期的 PR，请在描述中交代：

| 审查项 | 需要说明的内容 |
| --- | --- |
| 变更范围 | 涉及哪些层级、模块及外部调用方 |
| 设计依据 | 现有接口为何不足，是否可通过已有扩展点完成 |
| 兼容性 | 对既有 SDK、协议及下游插件的影响；是否需要迁移 |
| 依赖与分发 | 是否引入重复打包、ABI 冲突、平台或许可证限制 |
| 生命周期与并发 | 任务所有权、共享资源、取消、清理和异常路径 |
| 可观察性 | 失败时调用方如何获知状态及采取措施 |
| 开发者体验 | 对外接口、文档和 Example 如何同步更新 |
| 验证方式 | 如何复现关键行为与边界情况，结论和已知限制是什么 |

对于新增模块，优先证明它能够依照现有 Provider 契约接入，而不修改核心。无法满足某项约束时，应在 PR 中明确给出理由、风险和可行的替代方案，而不是隐式突破约定。
