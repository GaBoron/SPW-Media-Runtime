# 架构设计原则（Architecture）

> 状态：设计约束草案。本文规定 SPW Media Runtime 的长期架构目标与公共契约边界，不代表所述接口或模块已经实现。具体技术选型须在实现与验证后确定。

## 1. 目标与优先级

SPW Media Runtime 是供多个 SPW 创意工坊插件共同依赖的上游基础设施。其首要目标是**将相同的多媒体依赖集中分发、集中维护，供多个插件复用**，而不是让每个插件分别携带 FFmpeg、libmpv 等组件。

架构优先级：

1. **可靠与兼容**：Runtime 升级不应无故破坏已接入的插件。
2. **可扩展**：增加能力模块、平台后端或第三方依赖，不应要求重写 Runtime Core 或现有模块。
3. **共享依赖**：公共组件集中安装与管理；共享二进制不等于共享插件的运行状态。
4. **开发者友好**：稳定、简单、一致的公共 SDK；隐藏类加载器、原生加载和通信细节。
5. **按需运行**：未使用的模块不启动实际任务，使用结束后回收可释放的资源。

不把“尽快接入最多媒体库”作为首个稳定版的验收标准。

## 2. 架构分层与边界

```text
SPW Plugin A / B / C
         │
    Public SDK / API Contracts
         │
    Runtime Core（通用能力）
    ├── 能力发现、注册与版本协商
    ├── 调用方身份与权限边界
    ├── 任务、会话、事件与结构化错误
    ├── 生命周期、并发与资源调度
    └── 平台及依赖可用性查询
         │
     Module Provider Contract
         ├── Media Processing：FFmpeg / FFprobe
         ├── Media Playback：libmpv
         ├── Web Engine：WebView2
         ├── Metadata / Audio Analysis / Rendering
         └── Future Providers...
```

**核心不依赖具体媒体模块**：Core 不应硬编码 FFmpeg、libmpv、WebView2 或未来模块的类型、名称和逻辑。每个模块通过稳定的注册契约声明其能力、版本、平台、依赖、初始化与资源清理方式。

推荐区分：

- **Public SDK**：轻量、可独立引用的 API 契约，不携带大型媒体二进制或具体实现。
- **Runtime Core**：通用的注册、调度、状态、资源及权限管理。
- **Module Providers**：具体功能与后端实现；通过稳定契约接入 Core。
- **Native Assets**：按平台分发和管理的可执行文件、动态库及其他大型组件。
- **SPW Adapter**：宿主插件生命周期、权限和入口的适配，不让可移植模块依赖不必要的宿主内部实现。

模块可以拥有自己的次级依赖和子模块，但不得绕过通用的资源所有权与错误反馈机制。

## 3. 必须优先稳定的公共契约

| 契约 | 设计要求 |
| --- | --- |
| 能力注册与发现 | 稳定的能力标识、接口版本、平台/依赖条件及可用状态；允许注册未知的新能力 |
| 调用与通信 | 跨 PF4J 插件类加载器的兼容消息类型、参数校验、超时及请求关联标识 |
| 任务与会话 | 明确的创建、取消、关闭、清理流程；区分一次性任务和长期运行的会话 |
| 资源所有权 | 资源归属调用插件及其会话；共享资源跟踪使用者，不因单方退出被误释放 |
| 并发控制 | 独立任务可同时运行，必要时设置队列、配额、互斥和背压 |
| 状态与错误 | 同步请求结果、异步事件、最终任务结果、主动查询和结构化错误码 |
| 安全与隔离 | 插件身份、权限约束、凭据隔离、日志脱敏和原生组件故障边界 |

公共契约应同时规定成功路径、失败路径、取消路径以及版本不兼容的处理方式。

### 3.1 跨插件通信

SPW Workshop 基于 PF4J，不应假定两个插件可以安全地共享任意类实例或实现类。

- 公共 SDK 只包含稳定的协议和必要的数据类型，避免依赖第三方媒体库类型。
- 插件发现服务后进行协议/能力协商；不可用时返回可处理的错误，而非不明确的异常。
- 控制调用与状态事件可以通过合适的进程内协议桥接；不提前将某一种通信技术锁定为唯一实现。
- 高频视频帧和大块音频数据应使用专门的数据通道，避免逐帧通过通用消息通道复制与序列化。
- 不向调用插件泄漏可变的内部对象、原生指针或不明确的资源所有权。

### 3.2 状态、错误与可观察性

对外至少区分：

- **请求结果**：接受、拒绝、参数无效、权限不足、依赖/平台不支持等。
- **任务状态**：排队、初始化、运行、完成、失败、取消。
- **会话状态**：由模块定义播放、缓冲、暂停等细分状态；不得强迫所有模块共用不适当的状态机。
- **诊断信息**：稳定错误码、模块标识、调用插件标识、会话与操作标识、是否可重试，以及必要的上下文。

异步操作必须提供可观察的结束路径；长期会话必须可查询状态与最后错误。事件订阅方断线或插件卸载时，相关订阅应安全解除。日志不得包含 Cookie、令牌等敏感数据。

## 4. 共享依赖、并发及生命周期

### 4.1 一套依赖，多方复用

公共组件应由 Runtime 统一分发与管理，调用插件只依赖轻量 SDK。必须区分三件事：

- **共享安装文件**：避免同一媒体组件被多个插件重复打包。
- **共享已初始化的组件**：尽量复用兼容的底层服务，避免重复初始化。
- **独立运行会话**：播放器、处理任务和账户等由调用方独立管理；只有明确适合共享的采集/缓存服务才共享结果。

原生库和 ABI 版本存在冲突风险。不得假定同一 JVM 中任意版本的 FFmpeg 或 libmpv 可以安全共存；需要固定兼容版本、能力协商，必要时采用独立进程隔离。

### 4.2 按需加载与清理

- 未请求的模块不初始化其重型组件，也不启动持续后台任务。
- 仅在实际执行时创建播放器、转码进程、音频采集等活动会话。
- 最后一个使用者退出后释放对应会话、进程、句柄和临时资源；必要的共享服务可受控复用。
- JVM/操作系统可能无法安全卸载已加载的原生动态库：不承诺“任务结束就卸载 DLL/SO”。
- **延迟初始化不等于减少安装体积**；独立资源包或按需下载属于单独的分发设计。
- 插件失效、任务超时、取消或模块故障时，清理必须幂等，不得影响其他调用者。

### 4.3 失败隔离

单项操作失败不得错误地传播为所有模块不可用。高风险原生操作若无法提供进程内崩溃隔离，应评估独立进程执行。共享底层服务的故障必须明确广播给受影响会话，并支持重新连接或可恢复错误状态。

## 5. 可扩展性与兼容性

### 5.1 新模块不改核心

新增模块应能够通过既有 Provider 契约注册自身的能力、版本、依赖与资源管理方法，**原则上不修改 Core 原有代码、已发布 SDK 的既有接口或其他模块**。

新增功能应采用新增能力标识或接口版本，而不是向一个无限增长的全局接口直接堆方法。

如果新增需求确实暴露了基础契约缺口，先评估是否可以通过可选扩展、协议版本演进解决；不可兼容变更须明确发布为新主版本，并提供迁移路径。

### 5.2 版本管理

- **SDK/API 版本、能力协议版本、模块实现版本、原生依赖版本分别管理**，不可混为一个版本号。
- 公共接口遵循清晰的兼容规则：补充能力尽量采用向后兼容的方式，已有字段、错误码和行为语义不得随意改变。
- 调用方通过能力标识和所需接口版本判断可用性，不能仅凭 Runtime 总版本猜测。
- 对废弃接口先标记和给出替代方案，避免没有迁移期就删除。
- 原生库安全修复、许可变更、平台差异需在变更记录中说明影响范围。

### 5.3 平台支持

不同模块分别声明平台、架构、所需后端及能力限制。不能因为 Runtime 已安装就默认所有模块都可用。公共 API 应返回明确的模块不可用或平台不支持信息。

## 6. 稳定版发布门槛

首个供下游正式依赖的稳定版之前，应验证：

1. 已冻结并文档化核心契约、兼容规则、资源生命周期及错误语义。
2. 一个旧版调用插件不修改代码，仍能在兼容的 Runtime 更新后运行。
3. 新增独立 Provider 不需要修改 Core 现有逻辑。
4. 多插件同时获取、使用和释放同一公共依赖时，不产生资源串扰与误释放。
5. 缺少 Runtime、缺少模块、版本冲突、平台不支持或原生加载失败时，调用方能得到可诊断的结果。
6. 大型依赖只分发在公共运行时中，而不是因 SDK 或示例接入被再次打包到每个插件。
7. 示例、文档和公开 API 与发布版本一致。

目标是在初版设计阶段最大程度完整定义**稳定的扩展机制**，而不是预测未来所有具体模块。任何无法避免的破坏性变更都必须进行明确版本升级、风险说明及迁移支持。
