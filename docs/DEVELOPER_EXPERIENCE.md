# 开发者体验与文档贡献规范

本文适用于公共 SDK、接口命名、使用指南、API Reference、示例插件以及升级文档相关的 Pull Request。

SPW Media Runtime 的使用者应当能够**只依靠公开的访问接口与文档完成插件接入**。公共 SDK 应是最便捷、最完整的常规接入方式；直接访问底层组件则为需要自主控制的场景保留。开发者不应为了普通媒体操作而重复编写进程管理、参数解析或状态处理代码。接口的可发现性、错误诊断能力及示例的可复现性同样属于交付质量。

公共 SDK 的接口取舍与审查标准参见 [公共 SDK 设计与审查规范](./SDK_DESIGN.md)；底层模块与兼容性约束参见 [架构贡献规范](./ARCHITECTURE.md)。

## 1. 公共 API 的可用性标准

面向插件开发者的接口应遵循以下要求。

| 维度 | 贡献要求 |
| --- | --- |
| 首选接入 | SDK 应是常见需求的默认推荐方式，调用成本不应高于自行操作底层程序 |
| 轻量接入 | 公共 SDK 不携带共享组件的运行时实现或大型原生依赖，也不强制使用 SDK 完成全部操作 |
| 能力覆盖 | 常见功能提供完整封装；特殊参数及高级操作应有可扩展的 SDK 入口，不以预设方法限制底层组件能力 |
| 易发现性 | 能力名称、方法命名、强类型参数、KDoc 及 IDE 补全应清楚表达用途 |
| 简单优先 | 常见操作提供合理默认值和短调用路径，复杂能力再使用可组合的进阶接口 |
| 一致性 | 各模块在异步调用、状态、取消、事件、资源释放和错误语义上保持一致 |
| 细节封装 | 高级接口屏蔽通信与原生实现细节；底层访问通过正式的资源发现机制提供，不依赖内部路径 |
| 类型安全 | 避免无约束字符串、魔法数字和多个含义不清的布尔参数 |
| 生命周期 | 说明对象何时有效、由谁释放，明确线程及回调约束 |
| 故障可诊断 | 缺失 Runtime、能力不可用、版本不兼容、权限不足等情况给出可处理的结果 |

### 高级接口与底层访问

公共能力应根据实际使用场景提供不同深度的接口，并优先保证 SDK 的功能完整度与调用便利性：

- **SDK 常用接口**：为媒体探测、转码、播放、网页操作等常见任务提供清晰、类型安全的调用；负责底层初始化、参数组织、任务与会话管理、状态反馈及资源清理。
- **SDK 高级接口**：允许配置底层选项、组合复杂操作；对适合命令行调用的组件，提供通用参数执行入口，使调用方无需自行启动进程，也能使用高级封装尚未覆盖的功能，并继续获得托管任务的状态、取消和错误反馈。
- **底层程序访问**：允许获取 Runtime 管理的可执行程序，自行构造完整命令行和管理进程，例如直接调用 FFmpeg/FFprobe。
- **底层库访问**：在兼容性及资源安全条件允许时提供受支持的原生接口入口，不要求所有模块直接暴露原生句柄。

直接调用底层程序不应要求额外复制依赖，也不应依赖硬编码安装路径。资源发现接口应说明版本、平台、可用性、路径或访问句柄的有效期及更新时的行为。

**必须清楚区分两种执行模式的责任边界**：Runtime 托管调用可以提供统一的任务状态和错误事件；插件自行启动的进程则由插件处理退出码、标准输出/错误、取消及清理。文档不应暗示两者具有完全相同的状态反馈。

高级封装不应剥夺合理的底层使用需求，也不能以“支持直接执行程序”为由省略常用功能的 SDK 封装。提供新接口时，需说明其默认行为、可配置范围、性能与线程要求及不可覆盖的场景。

### IDE 与开发工具可发现性

公共 SDK 应以真实、稳定的 JVM/Kotlin 类型声明为基础，使 IDE 与使用源码分析的开发工具能够准确获取接口，而不是依赖字符串命令名或未公开的运行时反射结果。

- 服务入口、公开方法及参数应具有一致的命名、清晰的类型与必要的重载；合理使用枚举、选项对象或 DSL 提高补全质量，避免牺牲高级选项的可表达性。
- 公共类型和方法提供 KDoc，说明用途、参数、默认值、线程约束、返回结果、错误语义、可用版本和必要的使用示例；废弃接口须标注替代方案。
- SDK 应提供可供编译期引用的轻量发布产物，并随版本发布匹配的源码包（如 `sources.jar`）及可访问的 API Reference。文档可使用 Dokka 等工具从公开声明生成，但须与实际发行版本对应。
- 文档、公开源码与 Examples 应易于本地检索和构建工具解析，使 IDE、静态分析工具及编程代理能够核对真实方法签名和参数含义，无需猜测未发布接口。
- 接入示例需标明依赖配置和版本，并确保编译期所见的公共类型在目标 SPW 插件环境中具备兼容的运行时解析路径。

完整的自动补全依赖真实的编译期类型信息；仅提供基于字符串的通用调用入口，不能替代可发现、类型安全的常用 API。

## 2. 文档的结构与写作要求

文档要覆盖必要细节，但应围绕读者要完成的任务组织内容。建议遵循“**快速完成 → 理解选项 → 诊断问题 → 查阅契约**”的阅读路径。

| 内容 | 主要用途 |
| --- | --- |
| Getting Started | 从添加 SDK 到完成首次调用的最短可执行路径，默认展示推荐的 SDK 接入方式 |
| Guides | 面向一个具体任务的完整操作过程，包括边界与常见错误 |
| API Reference | 每个公开接口的定义、参数、返回值、错误、线程和生命周期约定 |
| Examples | 展示公开 SDK 与受支持的底层调用方式的可运行示例 |
| Troubleshooting | 按症状、错误码与平台定位问题的流程 |
| Migration / Changelog | 版本变化、兼容性、废弃功能及迁移操作 |

撰写或修改文档时：

- 在开头说明适用对象、前置条件和预期结果。
- 优先展示有效步骤，再解释影响使用的底层原因。
- 保持页面主题单一，使用准确标题与交叉链接，避免相同内容在多个位置重复。
- 包含必要的依赖、导入、权限、平台条件、参数和资源清理信息；不得通过省略关键步骤伪造简洁。
- 将 **尚未实现的设计提案** 与 **可直接使用的接口** 明确区分。
- 使用可搜索的正式错误码和术语，不要求读者阅读 Runtime 内部源码才能排查常见问题。
- 不把 README 扩写成完整接口手册；README 只承载项目介绍和文档入口。

## 3. API Reference 变更要求

新增或变更公共能力时，相应参考文档至少应包含：

1. 用途、适用模块、接口版本及平台支持。
2. 参数类型、单位、约束、默认值与返回值。
3. 同步或异步行为、回调线程、超时及取消语义。
4. 并发限制、资源所有权、生命周期和释放方式。
5. 稳定错误码、异常情况及调用方可采取的处理方式。
6. 最小完整调用示例及进阶指南链接；同时提供托管高级参数入口和底层访问时，需分别说明可用能力、资源定位、版本及执行责任边界。

优先由源码中的公共声明与 KDoc 维护接口事实，手写指南解释实际调用流程。变更接口语义时，应在同一 PR 中同步修改文档，避免源码与说明分叉。

## 4. Examples 的交付标准

示例代码是开发者文档的一部分，而不只是宣传材料。只有使用**实际公开、受支持的接口**（包括 SDK 或底层程序访问方式），并可以按说明构建运行的内容，才应标记为可运行 Example。

每个示例应具备：

- 明确的使用目标，以及最小、完整的构建配置和运行说明。
- 必要的导入、权限、平台限制和 Runtime/模块版本条件。
- 正常流程、相关失败处理、取消或退出时的资源清理。
- 独立于开发者本机目录、私人凭据和未公开资源的运行条件。
- 不重复打包 Runtime 已统一分发的原生组件；涉及直接调用时，展示资源发现、版本判断、退出码与清理行为。

示例按实际公开能力及开发者的典型使用场景组织，不预设固定工程名单、目录结构或模块实现顺序。应优先展示推荐的 SDK 用法，并在有必要时展示 SDK 高级参数调用与底层程序直接调用的差异。重要功能应有足够的示例说明常见用法、状态反馈和关键边界；未完成的示例不应以占位工程或不可运行代码冒充交付物。

简短代码片段可用于说明概念，但如果不是可执行 API，必须明确注明是设计示意。

## 5. 接入体验与升级维护

公共 SDK 的改动应同时评估首次接入和现有插件升级的成本：

- 开发者应能够通过公共入口发现能力、判断兼容性，并优先使用 SDK 完成常见操作；遇到高级需求时，可继续通过 SDK 扩展接口完成，必要时再选择底层组件调用。各方式的状态反馈与资源责任应清晰区分。
- 不应为了普通操作要求调用方知晓 Runtime 内部通信协议、原生句柄或组件安装路径。
- 需要的 Runtime 或模块未安装时，应给出清晰的可用性判断和对应解决建议。
- 弃用接口需提供明确替代方式；不兼容变更需提供 Migration Guide 和可识别的版本边界。
- 重要示例和 API Reference 应与对应发布版本保持一致，不能只维护面向最新开发分支的说明。

## 6. 开发者体验类 PR 的审查材料

涉及对外 API、文档或 Examples 的 PR，请说明目标使用场景、最短接入流程、错误处理方式及兼容性影响。审查重点包括：

- 首次接入是否需要额外的非公开知识，是否引入重复依赖。
- 常见任务是否通过 SDK 以清晰、少量的调用完成；复杂任务是否可以通过 SDK 高级接口表达，而不被迫直接管理进程。
- IDE 是否能够补全公开方法与参数；源码包、KDoc、版本化 API Reference 是否与实际接口一致并可由开发工具检索。
- API Reference 与实际接口是否一致；示例是否完整、可构建。
- 异常、权限与平台限制是否被准确说明。
- 如涉及升级，旧版使用者如何识别并处理差异。

对外标记某项能力为稳定可用之前，应提供与主要使用方式相匹配的接口说明、适用指南和可运行示例；如支持底层程序访问，还应覆盖该访问路径。鼓励未参与实现的贡献者仅依据公开说明完成接入，以发现隐藏前提或不必要的复杂度。
