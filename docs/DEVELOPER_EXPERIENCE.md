# 开发者体验与文档贡献规范

本文适用于公共 SDK、接口命名、使用指南、API Reference、示例插件以及升级文档相关的 Pull Request。

SPW Media Runtime 的使用者应当能够**只依靠公开 SDK 与文档完成插件接入**。可用性不仅取决于功能是否实现，也取决于接口是否容易发现、调用是否一致、错误是否能够诊断，以及示例是否真实可复现。

请与 [架构贡献规范](./ARCHITECTURE.md) 一并阅读。

## 1. 公共 API 的可用性标准

面向插件开发者的接口应遵循以下要求。

| 维度 | 贡献要求 |
| --- | --- |
| 轻量接入 | SDK 不应携带 FFmpeg、libmpv、WebView2 等运行时实现或大型原生依赖 |
| 易发现性 | 能力名称、方法命名、类型及 IDE 补全应清楚表达用途 |
| 简单优先 | 常见操作提供合理默认值和短调用路径，复杂能力再使用可组合的进阶接口 |
| 一致性 | 各模块在异步调用、状态、取消、事件、资源释放和错误语义上保持一致 |
| 细节封装 | 不要求接入方自行处理 PF4J 类加载、JMX/JNI、动态库路径及后端选择 |
| 类型安全 | 避免无约束字符串、魔法数字和多个含义不清的布尔参数 |
| 生命周期 | 说明对象何时有效、由谁释放，明确线程及回调约束 |
| 故障可诊断 | 缺失 Runtime、能力不可用、版本不兼容、权限不足等情况给出可处理的结果 |

高级封装不应剥夺合理的底层使用需求。提供新接口时，需说明其默认行为、可配置范围和不可覆盖的场景。

Kotlin 公共声明应包含有用的 KDoc；如有 Java 调用要求，应在接口和文档中明确兼容方式。避免仅依赖示例解释隐含行为。

## 2. 文档的结构与写作要求

文档要覆盖必要细节，但应围绕读者要完成的任务组织内容。建议遵循“**快速完成 → 理解选项 → 诊断问题 → 查阅契约**”的阅读路径。

| 内容 | 主要用途 |
| --- | --- |
| Getting Started | 从添加 SDK 到完成首次调用的最短可执行路径 |
| Guides | 面向一个具体任务的完整操作过程，包括边界与常见错误 |
| API Reference | 每个公开接口的定义、参数、返回值、错误、线程和生命周期约定 |
| Examples | 使用正式 SDK 构建和运行的独立 SPW 示例插件 |
| Troubleshooting | 按症状、错误码与平台定位问题的流程 |
| Migration / Changelog | 版本变化、兼容性、废弃功能及迁移操作 |

撰写或修改文档时：

- 在开头说明适用对象、前置条件和预期结果。
- 优先展示有效步骤，再解释影响使用的底层原因。
- 保持页面主题单一，使用准确标题与交叉链接，避免相同内容在多个位置重复。
- 包含必要的依赖、导入、权限、平台条件、参数和资源清理信息；不得通过省略关键步骤伪造简洁。
- 将 **尚未实现的设计提案** 与 **可直接使用的接口** 明确区分。
- 使用可搜索的正式错误码和术语，不要求读者阅读 Runtime 内部源码才能排查常见问题。
- 不把 README 扩写成完整接口手册；README 只承载项目介绍和文档入口。

## 3. API Reference 变更要求

新增或变更公共能力时，相应参考文档至少应包含：

1. 用途、适用模块、接口版本及平台支持。
2. 参数类型、单位、约束、默认值与返回值。
3. 同步或异步行为、回调线程、超时及取消语义。
4. 并发限制、资源所有权、生命周期和释放方式。
5. 稳定错误码、异常情况及调用方可采取的处理方式。
6. 最小完整调用示例及进阶指南链接。

优先由源码中的公共声明与 KDoc 维护接口事实，手写指南解释实际调用流程。变更接口语义时，应在同一 PR 中同步修改文档，避免源码与说明分叉。

## 4. Examples 的交付标准

示例代码是公共接口的一部分，而不只是宣传材料。只有使用**实际存在的公共 SDK**、可以按说明构建运行的工程，才应标记为可运行 Example。

每个示例应具备：

- 明确的使用目标，以及最小、完整的构建配置和运行说明。
- 必要的导入、权限、平台限制和 Runtime/模块版本条件。
- 正常流程、相关失败处理、取消或退出时的资源清理。
- 独立于开发者本机目录、私人凭据和未公开资源的运行条件。
- 不重复打包 Runtime 已统一分发的原生组件。

建议随相关模块逐步提供 `hello-runtime`、`ffmpeg-basic`、`video-playback`、`webview-session`、`audio-analysis`、`multi-session` 和 `error-handling` 等示例。**未完成的示例不应以占位工程或不可运行代码冒充交付物。**

简短代码片段可用于说明概念，但如果不是可执行 API，必须明确注明是设计示意。

## 5. 接入体验与升级维护

公共 SDK 的改动应同时评估首次接入和现有插件升级的成本：

- 开发者应能够通过 SDK 添加依赖、发现能力、处理版本不兼容、发起调用、监听状态并释放资源。
- 不应为了普通操作要求调用方知晓 Runtime 内部通信协议、原生句柄或组件安装路径。
- 需要的 Runtime 或模块未安装时，应给出清晰的可用性判断和对应解决建议。
- 弃用接口需提供明确替代方式；不兼容变更需提供 Migration Guide 和可识别的版本边界。
- 重要示例和 API Reference 应与对应发布版本保持一致，不能只维护面向最新开发分支的说明。

## 6. 开发者体验类 PR 的审查材料

涉及对外 API、文档或 Examples 的 PR，请说明目标使用场景、最短接入流程、错误处理方式及兼容性影响。审查重点包括：

- 首次接入是否需要额外的非公开知识，是否引入重复依赖。
- 常见任务是否能通过清晰、少量的调用完成，而复杂任务仍有扩展空间。
- API Reference 与实际接口是否一致；示例是否完整、可构建。
- 异常、权限与平台限制是否被准确说明。
- 如涉及升级，旧版使用者如何识别并处理差异。

对外标记某项能力为稳定可用之前，应完成其 API Reference、适用指南和至少一个实际可运行的 Example。鼓励由未参与该能力开发的贡献者仅依据公开说明完成接入，以发现隐藏前提或不必要的复杂度。
