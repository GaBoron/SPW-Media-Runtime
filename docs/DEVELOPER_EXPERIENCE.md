# 开发者体验与文档规范（Developer Experience）

> 状态：设计规范草案。本文描述未来公共 SDK、文档和示例的交付标准，不表示相应 API 或 Example 已可使用。

## 1. 核心目标

SPW Media Runtime 不只要让多个插件共享底层依赖，还要让**第三方开发者愿意使用、容易接入、出错时能够自行解决**。

开发者体验属于公共 API 的设计要求，而非功能完成后再补的附属工作。

衡量标准：在不阅读 Runtime 内部源码、不复制原生库、不理解类加载/通信实现细节的情况下，开发者应能依靠公开文档完成常见任务。

## 2. 公共 SDK 设计要求

### 简单操作必须简单

- 接入仅需轻量 SDK/API 依赖；不把 FFmpeg、libmpv、WebView2 等大型实现组件带入调用插件安装包。
- 统一的服务发现与获取方式；尽量在 IDE 中通过自动补全发现能力。
- 常见操作提供少量调用即可完成的高级接口，设置合理默认值。
- 复杂场景保留可组合的底层接口，但不迫使简单场景依赖底层细节。
- SDK 隐藏 PF4J 类加载隔离、JMX/JNI/进程通信、动态库路径和后端选择等实现细节。
- 使用含义明确的类型、枚举和对象，而非没有约束的字符串、数字常量及布尔参数组合。

### 一致性与可预期性

- 相似模块采用一致的命名、异步操作、取消、超时、事件、状态和错误风格。
- 所有公开 API 说明线程要求、阻塞行为和资源释放责任；避免隐藏的 UI 线程阻塞。
- 尽可能自动清理可控资源，并提供明确的显式关闭方式。
- 缺少 Runtime、模块未安装、接口版本不兼容、权限不足时，返回稳定且可定位的结果。
- 默认错误信息对开发者有用，同时避免泄漏敏感信息。
- Kotlin API 需有实用的 KDoc、良好的 IDE 类型提示；Java 兼容性视 SDK 目标明确声明。

### 建议的调用体验（仅为风格示意，不是已发布 API）

```kotlin
// 假想示例：实际命名、连接方式和资源处理以正式 SDK 为准
val playback = runtime.requireCapability<MediaPlayback>()
val session = playback.createPlayer()

session.open("video.mp4")
session.play()
```

真正的示例必须展示必要的获取方式、错误处理和资源清理，不能只截取理想化片段。

## 3. 文档信息架构

文档要**详尽、准确、结构清楚，但不重复和堆砌背景说明**。读者应能根据任务迅速定位：

| 文档 | 解决的问题 |
| --- | --- |
| Getting Started | 如何从零接入 SDK，并完成第一次调用？ |
| Guides | 如何完成播放、转码、会话管理、音频采集等具体任务？ |
| API Reference | 每个接口的参数、返回值、线程语义和失败方式是什么？ |
| Examples | 是否有可直接构建运行、便于改造的完整插件？ |
| Architecture | 为什么这样设计？扩展、兼容和资源归属规则是什么？ |
| Troubleshooting | 运行失败时如何判断原因并解决？ |
| Migration / Changelog | 升级后哪些行为变化，是否需要修改代码？ |

README 保持项目介绍和必要链接，不作为完整 API 手册。

### 编写规则

- **先给答案再给细节**：各指南开头明确适用场景、前置条件与预期结果。
- **一页解决一个问题**：不在快速开始里混入实现原理，不在 API Reference 里重复整篇教程。
- **代码必须完整且可用**：写明导入、依赖、运行环境、权限与资源清理；不要省略关键步骤。
- **准确区分计划与实现**：未发布的接口、平台和行为必须明确标识，禁止将伪代码误写成可运行示例。
- **按版本维护**：文档和示例与发布版本对应，旧版本保留可查的兼容信息。
- **可搜索和可导航**：统一术语、清晰目录、交叉链接，方便开发者从错误码直达解决办法。
- **避免废话**：不重复项目宣传、显而易见的代码语义或无助于操作的空泛解释。

## 4. API Reference 最低完整度

每个公开接口至少需要：

1. 简明用途与典型使用场景。
2. 参数类型、单位、约束及默认值。
3. 返回值、异步/阻塞语义和取消行为。
4. 线程安全、回调线程和并发限制。
5. 生命周期、资源所有权和清理责任。
6. 稳定错误码、异常及常见原因。
7. 所需模块、接口版本和平台支持。
8. 一个最小完整示例，并链接相关进阶指南。

尽量从源码中的 KDoc/类型声明生成参考信息；人工编写的指南负责讲清操作步骤与模块协作。两者交叉校验，避免长期分叉。

## 5. Examples 作为正式交付物

Example 不是 README 中的零散代码片段，而应是**可以独立构建、安装并运行的最小 SPW 示例插件**。每个示例都应：

- 带独立或明确复用的构建配置、必要权限和简短说明。
- 使用实际发布的 SDK，不直接引用 Runtime 内部实现或打包媒体原生库。
- 包含成功路径、相关错误处理和会话/资源清理。
- 不依赖私有账户、未公开文件或硬编码本机绝对路径。
- 尽量单一职责，便于复制到真实项目后修改。
- 标明适用平台、最低兼容版本和所需模块。

### 计划中的 Example

| 示例工程 | 演示目标 |
| --- | --- |
| `hello-runtime` | 检测 Runtime、发现能力、处理未安装/不兼容 |
| `ffmpeg-basic` | 媒体探测、转换任务、进度、取消和错误处理 |
| `video-playback` | 创建播放器、播放控制、画面输出和释放 |
| `webview-session` | 创建网页实例、持久化 Profile、清理会话 |
| `audio-analysis` | 订阅分析数据、停止订阅和共享采集 |
| `multi-session` | 多会话并发及互不干扰的资源管理 |
| `error-handling` | 结构化错误、模块不可用、超时和恢复 |

各 Example 随模块实际实现后逐步加入；不创建无法编译的占位工程冒充示例。

## 6. 第三方插件接入流程

正式的 Getting Started 应让开发者按下列最短路径完成接入：

1. 确认所需功能和平台支持。
2. 添加轻量 SDK 依赖，并确认不会将公共媒体库打入插件包。
3. 检测 Runtime 是否已安装、运行及支持所需接口版本。
4. 获取模块能力，创建任务或会话。
5. 订阅必要状态、处理错误与资源回收。
6. 构建插件，在目标 SPW 环境中验证。

对于常见失败，文档应直接给出可执行的定位路径，包括“Runtime 未安装”“平台不支持”“原生依赖加载失败”“权限不足”“版本不兼容”等，不要求开发者先阅读底层源码。

## 7. SDK 兼容与升级体验

- 每个稳定版提供可查的 API Reference、Example 和 Changelog。
- 兼容性变化准确标注受影响的能力及最低/最高支持版本。
- 废弃接口提供明确替代方案；不可避免的破坏性变更提供 Migration Guide。
- 错误码尽量稳定，新增错误类别不得悄然改变旧错误语义。
- 必要时提供轻量诊断工具或诊断信息输出，让插件作者能区分接入问题和 Runtime 自身故障。
- 对外发布的接口不应要求开发者跟随内部重构频繁改代码。

## 8. 发布验收

某项能力被视为“可供第三方正式接入”之前，应满足：

- 常用操作有清晰、易发现的 SDK 调用路径。
- 对应 API Reference、Getting Started/Guide 与至少一个真实可运行 Example 已完成。
- 示例无需携带重复的 FFmpeg/libmpv 等媒体依赖。
- 运行失败有结构化状态与明确排查办法。
- 兼容性及平台限制已标明。
- 开发者仅根据公开文档即可完成接入，无需参考 Runtime 内部源码。

在稳定版发布前，应尽量邀请未参与 Runtime 开发的插件作者依照文档独立完成一次接入，以发现 API 设计和文档中的真实障碍。
