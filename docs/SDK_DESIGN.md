# 公共 SDK 设计与审查规范

本文适用于新增、修改或扩展 SPW Media Runtime 公共 SDK 的 Pull Request，也可用于评估模块接口和配套示例的设计质量。

SDK 是插件使用 Runtime 的**首选接入方式**。优秀的 SDK 不仅要能调用共享依赖，还应将重复出现的媒体处理工作收敛到 Runtime 内部，使调用方专注于自身业务。直接访问底层程序或原生接口仍应保留，但不应成为实现常见需求的前提。

本规范关注公共接口的设计质量与审查依据，不规定具体 API 名称、示例工程清单或模块开发顺序。与 [架构贡献规范](./ARCHITECTURE.md) 和 [开发者体验与文档贡献规范](./DEVELOPER_EXPERIENCE.md) 一同适用。

## 1. 从使用场景定义接口

公共 API 的设计应从调用方希望完成的任务出发，而不是直接照搬底层库的函数、命令行参数或内部对象模型。

新增能力时，贡献者应先识别代表性的使用场景，并从插件作者的角度确认：

- **最短调用路径**：完成普通任务需要了解多少概念、配置多少环境、管理多少对象。
- **完整业务闭环**：调用方是否能够从请求发起一直处理到完成、失败、取消与资源释放。
- **复杂需求的表达能力**：高级参数、组合操作和非典型需求是否仍有受支持的实现途径。
- **复用价值**：哪些逻辑具有普遍性，值得由 Runtime 承担；哪些属于具体插件业务，不应固化进公共 SDK。

评估 API 时应优先审阅实际使用代码，而不只审阅接口类图或内部模块划分。简洁度不能仅以代码行数衡量：省略必要的状态处理、错误处理或清理步骤，不构成良好的开发体验。

## 2. 有层次的能力封装

SDK 应同时兼顾易用性与表达能力，根据需求复杂度提供合理的接入层次。

| 层次 | 设计要求 |
| --- | --- |
| 常用能力接口 | 使用清晰的动词、强类型参数和合理默认值完成典型任务；无需调用方理解底层命令或原生生命周期 |
| 高级配置与组合 | 可配置低层选项、组合多个操作，并保留必要的资源、性能与事件控制 |
| SDK 通用执行入口 | 对支持开放参数体系的后端，允许透传或构造完整参数，同时保留 Runtime 托管的进程、任务、取消、状态与错误处理 |
| 底层组件直接访问 | 为需要完全自主控制的调用方提供稳定的资源发现方式；自行执行时的进程与错误处理责任由调用方承担 |

**直接调用底层组件是兜底能力，不应替代高质量的 SDK 封装。** 如果典型需求必须绕过 SDK、自行解析媒体输出或编写基础设施代码，应首先检查 SDK 是否缺少必要抽象。

反过来，也不应为追求“一行代码”堆叠与业务场景强绑定的方法。相似操作优先复用组合能力、合理的选项类型和通用任务模型，避免大量名称相近、语义重叠的快捷方法。

## 3. 隐藏重复复杂度，保留必要控制

SDK 应承担跨插件反复出现、且适合统一管理的工作，例如：

- 能力发现、依赖定位、模块初始化与兼容性检查。
- 原生进程或播放实例的创建、调度、取消及回收。
- 异步执行、进度、完成状态与结构化错误反馈。
- 线程、回调、缓冲、资源所有权和必要的并发协调。
- 平台后端差异及可恢复故障的适配。

调用方仍应能够控制影响实际结果的重要参数，包括输出格式、质量、性能、缓存行为、超时及业务所需的事件订阅等。默认值应可解释、适合一般用途，并允许合理覆盖。

抽象应减少使用者需要承担的复杂度，而不只是将复杂度换一种名称暴露出来。只有底层实现真正提供相应保证时，才可承诺自动释放、硬件加速、跨平台行为或特定性能。

## 4. 易于发现与正确使用

公共接口应让开发者能够通过编译期类型信息、IDE 自动补全和简洁的接口文档发现功能。

- 使用清晰、一致的命名和强类型选项，避免将常见操作隐藏在字符串命令、魔法数字或不透明字典中。
- 通过参数类型、默认值及公开文档表达合法状态，尽量减少调用方自行猜测的组合约束。
- 明确异步与阻塞边界，避免意外占用 SPW UI 线程。
- 使任务、会话和资源的创建、使用、取消、关闭流程易于理解；常见路径不要求调用方手动拼接基础设施。
- 对失败提供稳定错误码、可查询状态和有意义的处理建议，不将底层日志当作唯一反馈途径。
- 公共类型和方法应具备与发行版本一致的 KDoc、源码包与 API Reference，以便人工开发者、IDE 和源码分析工具核实真实参数与行为。

当 API 的正确使用方式必须依赖阅读内部源码、复制未公开的实现逻辑或了解插件类加载细节时，应视为接口或公开文档仍需改进。

## 5. 稳定性与演进空间

Runtime 是下游插件的上游依赖，SDK 的易用性不应以持续破坏兼容性为代价。

- 公共入口、参数含义、错误语义和生命周期行为应保持可预期；新增能力优先采用向后兼容的方式。
- 新媒体能力应通过稳定的能力发现及 Provider 扩展机制接入，不应迫使旧插件或 Runtime Core 跟随每次扩展改写。
- 避免把第三方库的私有类型、原生指针或易变 ABI 直接固化为公共 SDK 契约；必要的底层访问应有清晰的版本与所有权边界。
- 不应在尚未验证真实调用场景前，过早将臆测的通用抽象固定为稳定接口。
- 既有抽象无法合理支持新需求时，应提出清楚的演进与兼容方案，而不是继续叠加含混的参数或隐藏行为。

接口设计的目标是**让未来的扩展主要发生在能力模块和新增接口层，而非反复修改已有契约**。稳定不等于拒绝演进，扩展性也不等于提前定义所有可能功能。

## 6. 以调用方视角审查 PR

影响公共 SDK 的 PR，应提供足够的使用证据，使维护者能够判断接口是否真正降低开发成本。建议展示具有代表性的调用代码或可运行示例，并说明：

| 审查维度 | 关键问题 |
| --- | --- |
| 上手成本 | 只了解目标任务的开发者，能否从公开入口找到并完成调用？ |
| 简洁程度 | 普通操作是否需要重复配置底层环境、管理进程或解析原始输出？ |
| 功能覆盖 | 常见功能是否可直接使用，复杂需求是否有合理的高级接口？ |
| 控制能力 | 是否暴露必要选项，同时避免强迫普通用户处理无关细节？ |
| 状态与清理 | 成功、失败、取消及退出路径是否完整且易于正确使用？ |
| 兼容与扩展 | 新能力是否能够独立演进，对已有调用方有何影响？ |
| 可发现性 | 方法签名、KDoc、源码与示例能否帮助开发者找到正确用法？ |
| 实现成本 | 新抽象带来的便利是否足以抵消额外维护、性能与兼容性负担？ |

对于已有直接调用方式的组件，可用同一任务对比 **SDK 常用接口、SDK 高级接口与底层调用** 的实际工作量。重点不是刻意制造代码长度差异，而是辨别 SDK 是否真正免除了可复用的底层工作。

审查应识别两类常见问题：

- **过薄封装**：仅将底层参数或进程调用换成统一入口，核心复杂度仍由插件作者承担。
- **过度抽象**：为了预想中的场景增加大量接口、隐式状态和难以理解的配置，反而提高学习及维护成本。

除非存在明确、不可避免的技术限制，普通媒体操作不应比自行调用共享底层组件更繁琐。对于性能敏感或特殊场景，应基于真实约束提供可选择的高级与底层路径。

## 7. 交付与文档一致性

公开 SDK 的变更应与使用指南、接口参考和适用示例一同交付。示例以真实使用场景组织，不预设固定名单，也不将设计伪代码当作可运行用法。

新能力在标记为稳定之前，应确保第三方开发者无需阅读 Runtime 内部实现，即可依据对应版本的公开资料完成接入、处理错误并正确释放资源。

详细的文档结构、发布工件与 Example 规范参见 [开发者体验与文档贡献规范](./DEVELOPER_EXPERIENCE.md)。
